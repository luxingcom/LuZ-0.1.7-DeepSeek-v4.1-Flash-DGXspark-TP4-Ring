## 一、本站 NCCL 现状核验

从 `~/nccl-debug/nccl-<node>-*.log` 实测：

```
NET/IB : Using [0]rocep1s0f0 [1]rocep1s0f1 [2]roceP2p1s0f0 [3]roceP2p1s0f1 [RO]   ← 4 NIC 全用
RING-ONLY v4 rank 0->3 chan 0 dev 0 / rank 0->1 chan 0 dev 1                    ← 仅邻接
Function | LL LL128 Simple | Tree  Ring | ...      ← 算法矩阵
AllReduce|  1    1     1   |   0      1  | ...     ← Tree 被禁用，Ring 强制
Broadcast/Reduce/AllGather/ReduceScatter 同（5 函数全 Tree=0 / Ring=1）
4 coll channels, 4 p2p channels
Symmetric memory is not supported. cuMemEnable 0, globalGinSupport 0, cuMemGdrSupport 0   ← 无 GDR
```

**结论：本站 Ring 强制在算法矩阵层已成立，比 `alexellis/switchless-nccl` 的公开补丁更彻底。**
对比：`alexellis/switchless-nccl` 的 `docs/patch-roadmap.md` 自述其补丁「让 Tree/PAT 建链函数返回成功
但不建连」——**留下算法矩阵仍声称 Tree 存在的隐患**（该仓库自己列为待办 "Make ring-only an algorithm
constraint — partially implemented"）。本站（LuZ 谱系）直接置 `Tree=0`，无此隐患。

**核验工具**：`scripts/nccl_selfcheck.sh`（校验 RING-ONLY 标记 / 算法矩阵 Tree=0&Ring=1 / 通道数 /
RoCE 设备数；仅记录 GDR）。已接入 `./start-tp4.sh ncclcheck`，并在 **serve 就绪后自动执行**
（非致命，失败打 warn）。

## 二、上游 ISSUE/PR 调研（按可采纳度排序）

### A. 立即采纳：上游 PR #17 — 共享专家 K padding（**无损 +1.1~1.5%**）

- **我们确实踩中**（启动日志已核验）：`DSV41 MXFP8 backend 'b12x' rejected N=5120 K=576`
- 根因：TP4 下共享专家 `down_proj` 的 K = 2304/4 = 576，不是 128 的整数倍 → b12x 拒绝 → 回退
  CUTLASS（128×32×128 tile，decode M=6 时把 M 补到 128 → 96256B smem → 每 SM 一块 → **GB10 48 SM
  上仅 25% 占用**）→ 实测 **52 GB/s**（该部件可跑 232-238 GB/s）。这是**唯一**被拒的 shape，但存在
  于全部 40 层。
- 修法：在 `_prepare_block_fp8_as_mxfp8` 之前把 weight 补零到 K=640、scale 补 1；调用时把输入经
  **常驻零缓冲**补到 640（CUDA graph 需稳定地址）。代价 14 MB/rank。开关 `DSV41_SHARED_PAD_K=1`。
- 实测：`cutlass K=576 58.0us → b12x K=640 17.2us`（−70.3%）；**净 −0.90 ms / 61.3 ms 步 = +1.47%
  预测**，稳态实测 prose +1.14% / code +1.51%。
- **无损**：0/30720 元素逐位相同，`max|diff|=0`。
- ⚠️ 关键注记（作者自述）：**单纯 padding 无收益**（CUTLASS 在 K=640 反而慢 0.7%）——收益全部来自
  「padded shape 获得 b12x 资格」。本站 `DSV41_MXFP8_BACKEND=b12x` ✓ 适用。**已采纳。**

### B. 高价值：上游 PR #7 — `EP_SIZE=2` 等四项（**+10.5%**，质量不变）

| 项 | 机制 | 实测 |
|---|---|---|
| **`EP_SIZE=2`** | EP4 时每 rank 持 96/384 专家、每步随机抽子集；TP 同步 → **步耗时付 4 rank 的最大值**。M=6 时每 rank 不同专家数 ~8.6±2.8 → 最慢 rank 多做 30-45% MoE 工作。EP2 减半 | **NCCL 每步 16.5 → 10.2 ms（−38%）**；all-reduce p90 479→350µs；≥200µs 调用 35(13.0ms)→18(6.2ms)；MoE grouped GEMM 不变（21.6→21.5ms）→ **是 straggler 修复，非带宽修复** |
| `DSV41_CACHE_GIB=4` + `CACHE_WAYS=16` | Engram 行缓存 | 命中率收益（本站用 1 GiB 即达 99.1%） |
| `--min-free-slots-delay 1` | 调度准入 | 恢复高位槽 |
| `--enable-deepseek-v4-fp4-indexer` | DSA indexer 的 FP4 kernel | kernel/精度选择（本站评估后开启，见 §十） |

- 总计 **+10.5% 均值**（conc1 +15~21%，conc2-4 +7.7~9.5%）；第二套 prompt 交叉验证 +9.8%；
  **decode step 69.0 → 61.0 ms 中位（−11.6%）**
- **质量不变**：75 个自动评分任务（代码跑隐藏断言 / JSON schema / 数值 / 格式 / 散文退化）逐步做
  McNemar 精确检验 → **零任务破坏，p=1.000**；长上下文检索另测 30/30
- **对本站意义最大的是 `EP_SIZE=2`**——NCCL 是环网的成本中心，−38% 直接打在痛点上。**已采纳。**

### C. 最高收益但需谨慎：SparkRing PR #267 — SGLang「decoder-tail prefill」（**64K prefill +57%**）

- **这就是「SIRCL 移植」问题的答案**：SparkRing 自己的 **SGLang** V4.1 配方**不使用 SIRCL**——用的是
  decoder-tail prefill + 换掉 pip NCCL
- 机制：V4.1 prefill 原本对全 prompt 跑完 40 层骨干；该配方在**全局 KV 源层之后，晚期 decoder 只处理
  末尾 128 个 extend token**（每条请求）
- 实测：**64K prefill 2,006 → 3,144 tok/s（+57%）**；20/20 首 token 选择一致 + 20/20 贪心续写一致
  （有界门禁）
- 另：**替换 pip NCCL 为预加载库**（规避 duplicate-NCCL，与我们用 `EP_SUPPRESS_NCCL_CHECK=1` 同类
  问题的另一种解法）；启动器做镜像/NCCL 身份校验、单行多 key、不把 key 暴露进 docker args
- 站点侧 6 小时 C8 浸泡：**13,224 请求零失败零挂起**，每波聚合中位 106.7 tok/s，可用内存地板
  28.47 GiB；20 分钟门禁 464 请求零失败
- 公共默认 context 262144；站点用 chunk 4096 / context 430080
- ⚠️ **风险**：decoder-tail 是**近似**（靠门禁一致性背书），须在站内用 needle 梯度 + 质量门禁复验后
  才可上产
- **本站状态**：同一机制在本站**已启用**（`--enable-decoder-swa-bounded-replay` 在现役 launch args
  中）。旁证：其记录的 64K prefill 3,144 t/s 低于本站 100K 的 3,238 t/s。→ **无需任何动作。**

## 三、SIRCL/sparkring 移植评估

**结论：不建议移植 SIRCL；应借鉴其 SGLang 配方的 decoder-tail prefill（本站已启用，见 §二 C）。**

| 维度 | 事实 |
|---|---|
| SIRCL 是什么 | SparkRing 自研集合通信层，把环上的 collective 排成**两个完美匹配**（0-1/2-3、1-2/3-0），使任何 rank 不必中继他人 collective 数据 |
| 谁在用 | SparkRing 的 **vLLM** 配方（GLM / 部分 DS 档）。**其 V4.1 SGLang 配方不使用 SIRCL**（PR #267 明示用 decoder-tail + 换 NCCL） |
| 移植到本站的障碍 | ① SIRCL 是 vLLM 侧集成（持久 RDMA session + graph-replayable command ring），SGLang 侧无对口接口 ② 本站 NCCL 已是 ring-only 且 Tree 已禁用，环内集体已走邻居——SIRCL 的收益面（消中继）在当前 `moe_a2a_backend=none` 下主要落在 MoE all-to-all ③ 与本站 LuZ 谱系 NCCL 分叉，须整链替换 |
| 真正的收益点 | 本站 `moe_a2a_backend=none` → MoE token 搬运与 TP 共用 NCCL 环 → 非邻接 all-to-all 绕环两跳。**PR #7 的 `EP_SIZE=2` 正是对这个成本中心的直接削减（NCCL/步 −38%）**，成本远低于移植 SIRCL |
| 若要进一步 | 先上 EP2（低风险、已有人验证）；仍不足再评估 SIRCL 级方案 |

## 五、600K 前端上下文容量评估

**场景**：前端按 600K ctx 使用。

**现役服务端限制（实测）**：`context_length` 600000 · `max_total_num_tokens` 9,600,000 ·
`max_running_requests` 16 · 代理并发 16。

**关键性质：池与并发是配套的。** KV 池**全局共享**，每个在飞请求占用 `prompt + 生成` 的 token，
所以「每会话可拿到的上限」= 池 ÷ 并发路数：

| `MAX_RUNNING_REQUESTS` | KV 池 | 满长并发下每会话可用 ctx | 与 600K 前端匹配 |
|---:|---:|---:|:--:|
| 12 | 5,000,000 | ≈ 417K | ✗ 差 183K（该组合下 12 路同时跑时，会话涨到 ~417K 即触发 KV 抢占） |
| 8 | 5,000,000 | ≈ 625K | ✓ 刚好覆盖，代价是放弃 c12 档 |
| **16** | **9,600,000** | **= 600K** | **✓ 现役配置**：池正好等于 16 × 600K，满 pin 无抢占 |

**端到端实测**：600K 冷 prefill 两次复现通过（341.7s / 348.3s），needle **PASS**，内存地板 4.92 GB；
632K 档亦通过（needle PASS，冷 prefill 430 s / 1472 t/s，memguard 最低 5.60 GB 无 abort）。

| 结论 | 依据 |
|---|---|
| **现役配置够用，无需改** | 9.6M 池 = 16 × 600K，满长 16 路即满 pin；600K/632K 实测通过 |
| **600K 冷 prefill ≈ 5–7 分钟**（真实成本） | 同口径随上下文衰减：200K 2483 → 500K 1913 → 632K 1472 t/s，非故障 |
| **c6 低点与本场景基本无关** | benchmark 的 c6 是「400 token 短输出」档；600K 前端 = 长输入 → prefill 主导，而 prefill 全面提升。**回退只存在于「中并发 + 短输出」角落** |

## 六、上游 PR #3 评估（switchless-ring 支持）

**它解决的是我们没有的故障**：stock TP4 profile 在 4 节点环上 NCCL 初始化失败——

```
NCCL INFO Trees [0] 2/-1/-1->0->-1
RuntimeError: NCCL error: unhandled system error
    at ncclTransportTreeConnect -> ncclCommInitRank
```

根因（PR 自述）：4 节点环上 rank0↔rank2 非直连；NCCL 在 ring 之外**额外建 tree**，而 **RoCE
queue-pair 建立不跟随 IP 路由** → tree 永远连不上 → boot 死。

**我们为什么没踩**：日志里同样有 `Trees [0] 2/-1/-1->0->-1` / `Connected all trees`，但我们的 NCCL
补丁把 **Tree 在算法矩阵里置 0**（见 §一），Tree 构造不参与后续 QP 建立，故不触发。

**其 env 契约与我们的对照**：

| 变量 | 我们的 NCCL | 我们当前设置 |
|---|:--:|---|
| `NCCL_ALGO=Ring` | ✓ | 已设 |
| `NCCL_MIN_NCHANNELS=4` | ✓ | 已设 |
| `NCCL_SKIP_TREE_CONNECT` | **✗ 不认得**（它/sparkring 自有补丁） | — |
| `NCCL_SWITCHLESS_RING_ONLY` | **✗ 不认得**（同上） | — |
| `NCCL_IB_SUBNET_PREFIX_LEN=24` | **✓ 支持** | 已 A/B 过，无效果（§十 B9） |
| `NCCL_P2P_LEVEL=SYS` | **✓ 支持** | 同上 |

**结论：不需要采纳**。两点价值：
1. **反证我们的手搓适配是必要的**——stock TP4 profile 在 4 节点环上根本起不来
2. 它带 323 行 `docs/switchless-ring.md`，可作**路由/校验项对照**，核查我们有无遗漏

- **实测确认前缀缓存工作正常**：同 prompt 冷 0.58s → 命中 0.26s（2.2×），`cache_hit_rate` 达
  **85.7%**、`cached_tokens_total{device}` 增长。读数为 0.0 只是因为基准流量用 uuid 前缀**故意**
  绕开缓存

### E. 待评估（按价值排序）

1. **`gate.sh` 化**——把 smoke + 门禁套件固化为 `./start-tp4.sh gate`，一键判定「可信」→ **✅ 已落地**

## 八、GB10 社区索引调研

[bidual/awesome-dgx-spark](https://github.com/bidual/awesome-dgx-spark) 是全社区 GB10 项目的索引。
**对我们最有价值的三个发现**（均与本站瓶颈直接对应）：

### ① NVFP4 KV 缓存 —— 同样显存换 3~3.5× 的 KV 容量

| 项目 | 说明 |
|---|---|
| [MiaAI-Lab/exllamav3](https://github.com/MiaAI-Lab/exllamav3) | ExLlamaV3 分支在 aarch64/GB10 上构建，**NVFP4 + FP8 paged-attention KV，每 GB 换约 3.5× 于 fp16 的上下文** |
| [drowzeys/keys-1M-CTX-Inkling-Small-…-SGlang-SM121](https://github.com/drowzeys/keys-1M-CTX-Inkling-Small-NVFP4-Dspark-NVFP4-KV-Cache-SGlang-SM121-optimized-on-Two-DGX-Sparks) | **给 SGLang 的 triton backend 加 NVFP4 KV**——池子放大 3.12× 到 1,082,627 tokens |

**为什么对我们重要**：KV 池是**当前唯一的硬约束**（现役 9.6M = 16 路 × 600K 已满 pin）。若 KV 能
压到 NVFP4，同显存下池子可数倍增长，换来更大的每会话上下文或更高的满长并发。代价是 KV 量化带来的
精度损失，需门禁验证。

### ② serving-mode —— 砍掉桌面栈换 10–15 GB 统一内存

[Entrpi/dgx-spark-serving-mode](https://github.com/Entrpi/dgx-spark-serving-mode)：三态 script，把
GNOME 与维护 timer 降到 `multi-user.target`，**省出 10–15 GB**。

**为什么重要**：GB10 上 host RAM 就是 GPU 内存。`MEM_FRACTION_STATIC=0.90` 下长 prompt 时 memguard
地板可低至数 GB——**10–15 GB 是质变**，可直接换成更大的 KV 池或更激进的上文。

### ③ autotune 竞态 —— 测量方差的一个机制性解释

[Weschera/Qwen3.8-27B-NVFP4-DFlash2-DGX-Spark](https://github.com/Weschera/Qwen3.8-27B-NVFP4-DFlash2-DGX-Spark)：
**boot 期一次 `fp8_gemm` autotune 竞态决定整个进程生命周期是 42 还是 33 tok/s**（±27%）。

**为什么重要**：我们多次观察到同配置下读数跳动，除碎片/干扰外，**这条给出另一个机制性解释**——若
我们也存在 `fp8_gemm` autotune 竞态，那单次 boot 的性能有随机性，需要固定 autotune 缓存路径
（SGLang 侧需确认对应开关）。

## 九、长档回归定位 A/B

### 触发

PR#17 / EP2 / PR#7 落地后的长档复测出现劣化：

| 深度 | 重启后基线 | 优化后 | 变化 |
|---|---:|---:|---:|
| 200K | 83.9s | 93.4s | −10% |
| 470K needle | 165.6s | 205.9s | −20% |
| 500K | 272.3s | 345.0s | −21% |
| 900K | 671.8s | 882.4s | −24% |
| 内存地板（900K） | 3.53 GB | **1.70 GB** | 减半 |

### A/B 结果（全部同一台机、同一窗口、同一 prompt 形状）

| 配置 | 500K 冷 prefill | 内存地板 | 结论 |
|---|---:|---:|---|
| 基线 EP4 bare | 338.7s | 8.23 GB | 参照 |
| EP4 + PR17 + fp4ind + min-free-slots | 595.4s | 10.22 GB | EP4 长档灾难 |
| EP2 + PR17 + fp4ind + min-free-slots | 345.0s | **1.70 GB** | EP2 大幅改善 |
| **EP2 + PR17 + min-free-slots（无 fp4ind）** | **307.0s** | **8.09 GB** | **该轮最优** |
| EP2 + PR17（无 min-free-slots、无 fp4ind） | 383.2s | 7.81 GB | min-free-slots 帮忙 |

### 三个结论

1. **当时形态下 `--enable-deepseek-v4-fp4-indexer` 对长档是净损失**：长档 −11% 且多吃 6.4 GB 统一
   内存，故该轮予以关闭。**注意这条结论绑定当时的 form**——现役形态（600K ctx / 9.6M 池 / 16 并发）
   重新评估后该开关为**开启**，理由是短输出档的代价很小（−6.4% / −0.9% / −3.3% @ c1/c8/c16）而被
   知情保留。**开关是 env 级、可逆的**，判断随 form 变化，不要跨 form 引用。
2. **EP2、PR17、min-free-slots 三项对长档都是净收益**（307 vs 对照 338.7 = 快 9%）。
3. **⚠️ 重要口径教训**：旧基线 272.3s（「整机重启后」测得）与同配置重测的 338.7s 差 **24%**——
   说明存在约 20% 量级的**「主机状态」影响**（刚整机重启 vs 已运行数小时）。这正是社区惯例
   「测量前重启」的原因。**本站纪律：A/B 必须在同一主机状态下对比，不能跨状态引用历史数字。**

### 该轮最终配置与验证

`EP_SIZE=2` + `DSV41_SHARED_PAD_K=1` + `--min-free-slots-delay 1` + 12 路 / 5M KV / 1M ctx。

- **GATE PASSED**（health + 算术 + JSON schema + 工具调用 + corruption 0/0/0 + code-gate 12/12）
- 并发：c1 82 · c2 117 · c4 220 · c6 237 · c8 287 · c12 **379**
- 三轴：decode 峰 97.5 / 均 79.5、prefill 8K 3032
- 500K 冷 prefill **309.6s / 1686 t/s**（复现 307.0）

## 十、B9 / B10 A/B

### B9 — NCCL 两变量（PR#3 派生）**无效果**

加 `NCCL_IB_SUBNET_PREFIX_LEN=24` + `NCCL_P2P_LEVEL=SYS`（我们二进制支持但用默认）后：

| 轴 | 参照（无这两项） | B9 |
|---|---:|---:|
| c12 | 375-379 | 371 |
| prefill 8K | 3032 | 2998 |

均在噪声内 → **已撤销**（与预判一致：本站 fabric 本就是 /24 子网、单卡节点 P2P level 无关）。

### B10 — Engram 行缓存 **是大赢**

`DSV41_CACHE_GIB=1` + `DSV41_CACHE_WAYS=16`（上游建议 4 GiB；我们先用 1 GiB 试探）：

| 轴 | 无缓存 | **1 GiB 缓存** | 变化 |
|---|---:|---:|---:|
| decode 峰 / 均 | 97.5 / 79.5 | **100.7 / 81.7** | +3.3% / +2.8% |
| c8 | 287 | **297** | +3.5% |
| **c12** | 375-379 | **399** | **+6.0%** |
| prefill 8K | 3032 | **3101** | +2.3% |
| prefill 32K | 3279 | **3483** | +6.2% |
| prefill 100K | 2931 | **3238** | **+10.5%** |
| 500K 冷 prefill | 309.6s | **298.5s** | +3.7% |
| Engram 命中率 | 0%（无缓存） | **99.1%** | — |

**结论**：Engram 行缓存对**解码与长 prefill 双向受益**，且仅用 1 GiB 就拿到接近饱和的命中率
（99.1%）。**已采纳**。内存充足。GATE PASSED。

> 机制注记：`DSV41_CACHE_GIB=0` 的直觉理由是「packed 单读已够、缓存占内存不值」——实测证明缓存
> 把 Engram 读从「每次查都读盘」变成 99% 命中，收益远超 1 GiB 内存的成本。

## 十一、C 档与剩余 B 档的处置

### C13 — decoder-tail prefill：**我们已有，无需移植**

见 §二 C。核心机制 `--enable-decoder-swa-bounded-replay` 已在现役 launch args 中。

### C14 — compact ragged verify：**仍被上游阻塞**

[sgl-project/sglang#39173](https://github.com/sgl-project/sglang/issues/39173) 仍 open
（engram target-verify 断言）。本站 `SGLANG_RAGGED_VERIFY_MODE=static` 是正确规避。
**待上游修复后重测。**

### C15 — 换 switchless-nccl 构建：**评估后不采用**

- Alex 的 `switchless-nccl` 与本站 LuZ 构建**同为 NCCL 2.30.7**，走不同补丁路线
  （`SWITCHLESS_RING_ONLY` vs 算法矩阵 `Tree=0`）；本站路线**更彻底**（Tree 在矩阵里 = 0，而它的
  tree 连接函数只是"假装成功"）。
- 其宣称的「C4 +10.8%」是**它自己栈内的前后对比**，非与本栈的可比口径。
- 换构建需整链替换 + 重新验证，风险大于预期收益。**不采用**；若将来 LuZ 构建出问题，它是一个现成
  的替代选项（Apache-2.0、有版本化 release）。

### B7 — c6 低点：**已定性为 EP2 的可接受代价**

|c4|c6|c8|c12|
|---|---:|---:|---:|---:|
| EP4（原始） | 210 | 260 | 264 | 271 |
| EP2 | 221 | **237** | 287 | **399** |

c6 从 260 降到 237（−9%），但 c8 +9%、c12 +47%、长档 prefill +9%、peak +3%。**EP2 是全局更优**，
c6 一点是同一条曲线上的局部凹陷（可能源于 EP2 下 6 并发恰好落在某种专家分布劣化点）。
**维持 EP2，不再追。**

### B8 — hybrid MLA backend：**评估后暂不采用**

做法是按 query 长度分流（短 decode → FlashInfer/split-K，长 prefill → SM120 Triton sparse-MLA）。
本站现状 `--attention-backend dsv4` 且 `dsv4_prefill_backend=auto`——**SGLang 已内置自动选择**。差异
在于上游补丁做了更激进的显式分流。考虑到：① 需新增并验证一个内核分派补丁 ② 本站 prefill 属同类栈
前列 ③ 该补丁的正确性只有作者单方面验证 —— **暂不采用**，列为后续 A/B 候选（若将来 prefill 成为
瓶颈）。

### B12 — STS 校准表：**被上游 bug 阻塞（不可为）**

按步骤执行得到的是**引擎级证据**而非推测：

1. 以 `SGLANG_DSPARK_STS_COLLECT_PATH=/state/sts-shards/sts` 启动（该环境变量确已进容器），灌 24 条
   多样化请求（code/count/散文/JSON/数学/工具），**零 shard 产出**。
2. 查 SGLang 源码定位原因：
   - `dspark_observability.py:936` — `if not self._planner.carries_confidence: return`
   - `dspark_planner.py:210` — `def carries_confidence(self): return self._confidence_head is not None`
   - `dspark_planner.py:124` 的告警原文：**"DSPark STS calibration path given but no confidence head
     present (static mode / head-less checkpoint); ignoring"**
3. **引擎自身日志给出判决**：
   ```
   --speculative-dspark-sps-table-path feeds the ragged-verify budget scheduler,
   which is off under SGLANG_RAGGED_VERIFY_MODE=static; it will be a no-op.
   ```

**结论**：STS 采集要求 **compact/ragged verify 模式**（该模式才装载 confidence head）。而 compact
模式在 V4.1 + Engram 上触发 `engram target-verify` 断言崩溃（= [sglang#39173](https://github.com/sgl-project/sglang/issues/39173)，见 C14）。

→ **B12 与 C14 同源，同样被上游阻塞，当前配置下不可执行。**

⚠️ **附带事实（重要）**：同一条日志说明**SPS 表在 static 模式下同样是 no-op**。即 DSpark 的
ragged-verify 排程增益**当前并未生效**（这正是上游 PR#7 声称 +10.5% 的那部分）。SPS 表保留无害
（compact 修复后即可生效），但**不应把已有收益归因于它**——实测的 c12/长档提升来自 EP2、Engram
缓存、PR17 与碎片清理。
