## 二、形态 B 的优化复测（三批，2026-09-13）

### 批次 1 — SparkRing 对照后的逐项处置

参考 `FujitsuPolycom/sparkring`（同为 GB10 无交换机环网栈）逐项对照后实施：

| 项 | 结论 | 动作 |
|---|---|---|
| worker packed Engram | **发现真 bug**：3/4 rank `packed=False`（2 次读/查询）；根因 = worker `.env.tp4` 的 `MODEL_DIR` 指向不存在路径，`cmd_pack` 挂到空目录仍报成功 | 修 `cmd_pack`（local 模式挂 `WORKER_MODEL_DIR`）+ `model_src` 加断言；重跑 pack + 重启 |
| Engram 列平衡 | 本站连续行切分**无失衡**（四 rank 各 96.0M 行、读取量相等），SparkRing 的列交织问题不适用 | 不改 |
| `NCCL_SWITCHLESS_RING_ONLY=1` | 本站 ring-only NCCL（LuZ 自建）**不认识该变量**；通道数已是 4 | 不改 |
| 路由/转发 | `ip_forward=1` 已开、路由表仅直连 4 条 fabric 子网、rendezvous 走管理网 → 干净 | 不改 |
| `--max-num-seqs` | 8 → **12**（含 CUDA graph bs=12） | 已改 |
| 重启清碎片 | 主机重启**受阻**（`vllm-v4v-head.service` enabled，重启会拉起另一栈抢 GPU） | 改容器级重启，后经授权做整机重启 |

**逐项归因**：

- **PR#17（共享专家 K padding）**：`rejected N=5120 K=576` 计数 **1 → 0**，`b12x accepted the shape:
  True（43 层已 padding）`。峰 +0.9%、散文 +1.3%（与上游自报 prose +1.14% 吻合）。**质量零变化**

- **PR#7 `EP_SIZE=2`**：峰 +6.6%、均 +7.3%、c8/c12 +4~5%。机制是 **straggler 消除**（EP4 时最慢

### ⚠️ 两个必须知道的运维事实

**① 引擎运行时长会劣化长档性能约 23%**

| 500K 冷 prefill | 耗时 | 吞吐 |
|---|---:|---:|
| 新鲜引擎（boot 后 ~15 分钟） | **273.8s** | 1918 t/s |
| 同一引擎跑 ~1h20m 重负载后 | 354.7s | 1478 t/s |

同一配置、同一 prompt，仅引擎「年龄」不同 → **长 prompt 吞吐衰减 ~23%**。社区同源纪律：
「测量前重启」。**建议**：长上下文密集使用前重启引擎；或纳入定期重启维护。

**② 900K 单条 prompt 在形态 B 下不可用（配置容量问题，非引擎累积）**

- 新鲜引擎上同样失败：`prompt_tokens=0`、memguard 触到 **1.50 GB** 阈值（abort 线）
- 对比：**未加 Engram 缓存 / K-pad 之前**，900K 的内存地板是 **3.53 GB**（成功）
- 差额 ~2 GB 来自 **Engram 缓存（1 GiB）+ K-pad 的输入缓冲**（900K 行 × 640 ≈ 1.15 GB 按需分配，
  43 层反复）
- **600K 及以下不受影响**（实测：**600K 两次复现均成功**，needle PASS，内存地板 **4.92 GB**）

**处置建议（择一）**：
- 若前端上限就是 600K → **无需动作**，600K 实测安全（地板 4.92 GB，余量充足）
- 若需要 900K+ → ① 关 Engram 缓存（`DSV41_CACHE_GIB=0`，代价 c12 −6%）或 ② 上社区
  **serving-mode**（砍桌面栈省 10–15 GB，一次性解决且顺带扩大 KV/上下文空间）
  （见 [上游调研 §八 ②](4DGX-dsv41-上游调研-20260913.md)）

## 三、结论画像

**dsv41 = prefill 王者 + 单流中等 + 高并发中上。**

- **prefill 全面优于历史方案**：8K 2814 = GLM 的 1.30×、Vision 的 1.69×、LuZ 的 1.87×；
  100K 3119 = 历史最好 2430 的 1.28×。对 agentic 短平快（大量短 prompt）与长文档冷加载场景是净收益。
- **单流 decode 89.6 = LuZ 的 67%、Vision 的 83%、GLM 的 95%**——V4.1-Flash 参数量级（≈550 B MoE，
  8B/16B 激活）的单流代价；story 型 29.4 与上游 37.9 同量级，code 型 89.6 是上游单流 2.4×
  （TP4 vs 其 TP3 + 环网适配的收益）。
- **并发聚合**：c2 反超 Vision OFF 79%，c4-c12 与 Vision 打平；c12 271 = LuZ 444 的 61%——高并发下
  LuZ 的 W4A4 + DSpark k=7 仍是天花板。
- **thinking ON ≈ OFF**（90.0/72.3 vs 89.6/72.1，c6 +17）——与 Vision 的「免费 + 高并发档」
  （c8 +66%）不同，V4.1 的思考模式不改变聚合画像；唯一例外是**散文 +9%**（30.8 → 33.6 t/s，
  可预测文本的投机增益）。
- **散文单流 30.8 t/s（OFF）/ 33.6（ON）**：长文本生成是 dsv41 最慢的形态（= Vision 的 73%）；
  重度散文/创作流量的速度体感会明显低于 Vision-Exp 与 LuZ。
- **长档**：400K 档落后 GLM（其优势域，1.76×），但 900K 可用且 needle 正确；dsv41 胜在中短 prefill
  与 1M 满窗可用。

**一句话**：换 dsv41 用单流速度（−17%~−33%）换 prefill 大幅领先（+28%~+87%）——适合 prompt 密集 /
长输入重读的流量形态；若流量以长对话 decode 为主，LuZ0.4.5 仍是单流/高并发王者。

## 四、质量门禁与事件矩阵

口径：5 分钟零负载确认（`num_running_reqs=0` 连续 15 轮）→ 冷启动 → 串行执行。频率 2281 MHz。

| 项 | 结果 | 对照 |
|---|---|---|
| **冷启动惩罚** | 冷态 count300 89.7 t/s vs 收尾 warm 89.5——**无冷惩罚**（boot 预热生效） | Tony vLLM 是 −30% |
| **needle 30K**（29005 tok） | ✅ PASS，4.3s | LuZ 门禁同款 |
| **needle 229K**（221142 tok） | ✅ PASS，79.8s，2772 t/s | ✅ |
| **needle 470K**（453822 tok） | ✅ PASS，200.8s，2260 t/s | GLM 历史 229K/470K 全过 |
| **corruption probe** | U+FFFD **0/0/0** ✅ | Tony ModelOpt 4/9/8、RedHatAI 0/0/0 |
| **终止性** | temp 1.0 **18/18**、temp 0.6 **18/18** ✅ | Tony 18/18 与 14/36 |
| **code-gate** | **12/12** 无坏输出 ✅ | Tony 口径 12/12 |
| **vision 双方向** | 红左蓝右 + 反序双方向 ✅，img_tokens=652 @1024²（分辨率自适应），0.9-1.4s | 0xSero 1024 image token 口径 |
| **GSM8K n=50** | **50/50 = 1.00** 双口径（content/marker），0 错误，mean 2.6s/题、142 tok/题 | Tony Patch5 后 0.98 |
| **DSpark 流量画像** | 代码流 accept_length **3.95** tok/step / rate 0.59；GSM8K 数学流 **6.0** / **1.0**（打满） | Tony vLLM 均值 3.57 |

**事件矩阵（18 格，0 错误）**：512-131072 × c1/c2/c4，common-window 重叠窗交付吞吐——c1 **59-63**、
c2 **91-100**、c4 **136-146** t/s（输入尺寸无关，稳定）；**burst 最大间隙 80-140 ms**（输出流无长
停顿；上游 p50 23.6 ms 同量级）。

**执行注记**：① needle 需 token 精确构造（早期用字符口径导致实际深度仅 ~1/5）；haystack 构造需增量
计数（重编码 O(n²) 卡死教训）。② GSM8K 脚本含 3 处占位路径，已修 dsv41 副本（`gsm8k_dsv41.py`）
且 raw 行可独立判分。③ 矩阵用 `matrix_v1.py`（/v1 等价实现——权重目录无作者自定义 encoding/ 模块）。
④ 全部完成后维护旗已清、自愈 monitor 恢复巡逻。

## 五、思考模式横向

| 方案 | 思考语义 | 开思考的影响 | 交互建议 |
|---|---|---|---|
| LuZ0.4.5 / 0.3.1 | 引擎默认 ON | 基准即 ON 口径 | 默认即可 |
| **Vision-Exp** | OFF/ON 双档实测 | **ON =「免费 + 高并发档」**：单流持平（107.8 → 108.1），c2 +119% / c6 +85% / c8 +66%；散文 42.2 | 建议 ON |
| GLM-5.3-Flash | 显式 ON | — | 默认 |
| **dsv41（V4.1-Flash）** | effort 预算 1-100 | **≥50 在图片分析题上发散**（见下表）；散文 ON 反升 +9%（30.8 → 33.6） | **慎开**：交互用 关闭 / 低(25) |

**dsv41 思考预算实测（1440×900 图 + 颜色统计题，TP4 引擎直连）**：

| 档位 | 耗时 | 结果 |
|---|---:|---|
| 关闭（none） | 4-7s | ✅ 正常答案 |
| low（25） | 17.8s | ✅ 正常答案（思考 ~690 tok） |
| high（50） | 80s | ❌ 思考 4355 tok，答案为空（`finish=length`） |
| xhigh（75） | 74s | ❌ 同上 |
| max（100） | 32-42s | ❌ 同上 |

**结论**：dsv41 的思考模式与 Vision-Exp 恰好相反——Vision 是「开思考免费提速」，dsv41 是「开思考
至少在图片类问题上发散」，副作用即客户端侧「新会话 TTFT 30-80s 且答不出内容」。门户已按此定档
（滑条 关闭/25/50/75，不做 max 升级）。

## 六、批判性注意点

1. **`bench_v2` 计时字段对 SGLang 失效**（ttft 0.0001 假值）——PR400K 只有墙钟口径可用；若需精确
   conc2 时序，需修其 SSE 解析或改用 `prefill_distinct` 单流法。
2. **compact ragged-verify 未用上**：上游预期吞吐来自 compact + SPS；本站 static 模式下 c12 聚合可能
   低于上游 TP4 理想值——上游若修 engram target-verify 断言（
   [sglang#39173](https://github.com/sgl-project/sglang/issues/39173)）可再试。
3. dsv41 单流数据在 warm 状态测得（口径同历史）；冷启动首 token 含 autotune 不在此轴。
4. STS 校准表未做（被上游 bug 阻塞，见 [上游调研 §十一 B12](4DGX-dsv41-上游调研-20260913.md)），
   `spec_accept_rate` 尚有校准空间。
5. **测量前必须确认 `num_running_reqs=0` 且 `num_queue_reqs=0`。** 曾出现一次异常读数
   （decode 峰 66.6 / 均 54.6，均匀 −26%）而 **prefill 完全正常**——查因是测前有 1 个在飞请求 +
   面板双轮询叠加；GPU 频率、温度、降频标志均无异常（2288 MHz / 59°C / 0x0）。
   **判读要点：decode 均匀劣化而 prefill 不变 = 批次争用，不是配置退化。**
