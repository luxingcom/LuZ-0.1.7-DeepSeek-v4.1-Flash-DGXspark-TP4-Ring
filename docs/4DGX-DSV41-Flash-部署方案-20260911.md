## 二、部署形态决策（5 条）

1. **本地权重，跳过 NFS 全链路**：四机已有 476G 权重，repo 的 NFS share 机制整体弃用——消除 exports
   覆写跨栈风险（作者脚本会覆写复用容器的 /etc/exports）+ rank3 免环上两跳读。
2. **接管 8899 loopback**：proxy 与门户 LiteLLM 条目、hermes、RK 面板全部零改动。对照 09-05 先例
   「PORT 8001→8888，免改门户 config」同思路——本次连 proxy 都不用碰。
3. **契约复刻**：`API_KEY=YOUR_API_KEY`；served name 保留旧名 `deepseek-v4-flash-vision-exp`
   （proxy 转发的就是它）并新增 `deepseek-v4.1-flash`。
4. **环网 env 沿用已验证值**：GID=-1 铁律（绕过 repo 的自动探测）、NCCL 挂 `/opt/nccl-ringonly`、
   `MERGE_NICS=0`、`SUBNET_AWARE_ROUTING=1`、PEER_HCA per-rank。
5. **TP4 未 boot 验证 → 保守起步**：CONTEXT/MAX_TOTAL_TOKENS 先取小值跑通，再爬坡到现役
   **600000 / 9600000**（爬坡过程与容量上限见 §五 Phase 3）。

## 三.2 RK3588 监控面板适配（sparkdash）

实测结论：面板（`/opt/sparkdash`，LlmProbe.js）**已有 SGLang 适配代码**，切换后自动检测可命中
（`/get_server_info` 兜底探测），不会挂——但 4 张卡会空，需一个小补丁补全。

**自动工作（无需改）**：

- 后端检测：`/v1/models` owned_by 嗅探失败时 probe `/get_server_info` → OK 即判 sglang（dev-dsv41 有
  该端点，deprecated 但可用）
- 硬件层：sparks.json SSH 轮询 nvidia-smi 与推理栈无关，零改动
- 累计 token：token bank（`/opt/sparkdash/data/token_usage.json`）跨引擎重启增量容错已实现，切换不归零

**会变化/退化（需适配）**：

| 面板卡片 | 切换前（vLLM） | 切 dsv41 后 | 适配 |
|---|---|---|---|
| gen/prefill tok/s | ✅ | ✅（需 `--enable-metrics` 才走计数器 diff；否则退化为 sticky gauge 6s 窗口，且 prefill 无） | 部署侧加 `--enable-metrics` |
| 累计输入/输出 | ✅ | ✅ | 无 |
| 并发槽 | 12（`--max-num-seqs`） | 16（`MAX_RUNNING_REQUESTS`） | 预期变化，非故障 |
| 上下文长度 | 600000 | 600000 | 无 |
| KV 卡 | `vllm:kv_cache_usage_perc` | ❌ 空（SGLang 模式未接） | LlmProbe.js 补 `sglang:kv_cache_memory_usage_gb`（GiB 单位，前端需适配或换算） |
| TTFT 卡 | `vllm:time_to_first_token_seconds` | ❌ 空 | 复用 histogram 解析器换前缀 `sglang:time_to_first_token_seconds` |
| MTP/投机卡 | `vllm:spec_decode_*` | ❌ 空 | 补 `sglang:spec_accept_rate` |
| 队列卡 | `vllm:num_requests_waiting` | ❌ 空 | 补 `sglang:num_queue_reqs` |

**面板补丁范围**：仅 `server/collectors/LlmProbe.js` 一个文件（`_applySglangServerInfo` /
`_applySglangMetrics` 各加几行）+ `systemctl restart sparkdash`。所有补的指标名已在 dev-dsv41 镜像
`metrics_collector.py` 中核实存在。前端如需 KV 卡单位适配（GiB vs %）另改。

**面板修复记录**：① 累计丢失——SGLang 路径裸计数器覆盖 `totalOutputTokens`，未走 token bank → 改为
与 vLLM 同款 `bankTokenCounters` 记账；② 实时不显示——`/metrics` 获取被 sticky gauge 门控挡住 →
取消门控；③ 生成期间 genTps 恒 0——SGLang token 计数器**请求完成时才记账**（vLLM 是实时）→ 补
`sglang:gen_throughput` live gauge 路径（仅 `requestsRunning>0` 时信任，防粘滞）；④ **cached 口径**
——SGLang `prompt_tokens_total` **含** cached（vLLM 不含，语义相反），未拆分导致 miss/hit 计费错 →
LlmProbe 改 `computed = prompt − cached` 分别入账（cached 恢复增长）；⑤ **dashboard 独立轮询只解析
`vllm:*`** → 加 `sglang:*` 双解析 + `sglang:cache_hit_rate`（面板自己那套指标与 sparkdash 是两条
独立链路，这是"数字不一样"的根源）；⑥ **趋势曲线崩**——旧 bug 窗口期把当日基线 `baseOutput` 定成裸
计数器值(=8) → 当日曲线 = 绝对总量 39.8M 拉爆、前 6 天压平 → 用午夜 bank 实测值重定基线并清污染点；
⑦ **费用曲线 cached 双重计费**——曲线取 `input_total`(=computed+cached) 乘 miss 价、cached 又乘 hit
价 → 改取 `input`(computed) 与 `_day_cost_from_hist` 同口径（实测虚高 8.78 → 修正 7.36）。

**金额口径与验证**：单价表 `PRICE_SCHEDULE`（高峰 miss 2.0 / hit 0.04 / out 8.0，闲时对半；高峰 =
工作日 9-12、14-18 北京时）。独立重算对账：今日金额 = ¥7.3584，面板显示 7.36 ✅。

**注意**：`/get_server_info` 在 dev-dsv41 中**不返回** `total_input_tokens/total_output_tokens` 顶层
字段（源码已核实），面板主路径靠 `/metrics` 计数器——因此 `--enable-metrics` 从"可选"升为"面板必做"。

## 六、风险与红线

1. **TP4 profile 上游从未 boot 过**——本阵列是首跑，`MEM_FRACTION_STATIC=0.90` 等值全是推算。
   首 boot 失败不意外，Phase 4 回退兜底。
2. **性能差距**：上游单流 37.9 tok/s vs 现役（见 [README §2](../README.md)）。门户无感 ≠ 终端用户无感。
3. **窗口内禁重启机器**：`vllm-v4v-head.service` enabled，重启自动拉起 v4v 栈抢环网（GLM 同坑先例）。
4. **基础镜像可变 tag**：`dev-dsv41` 未锁 digest；四机曾 pull 到同一份，**下次重拉前锁 digest**。
5. AGPL-3.0：仅自用部署无传染风险，不改其代码再分发即可。
6. 上游作者 3 机三角形 / 4 机交换机假设与本站环网不同——所有拓扑相关默认值已按 §四 覆盖，其余
   （镜像/权重/Engram/DSpark）照搬。

### 关键事件：LuZ 自愈链反扑与停靠方案

`vllm-tp4-head/worker.service`（`Restart=always`，monitor 为主进程）在容器被删后自动重建 LuZ，
而部署账号无 sudo 无法停单元。rootless 停靠方案：占位容器（alpine sleep infinity）占住
`vllm-tp4-rankN` 名 → monitor `docker wait` 停靠；再 `docker rename` 改名为 `dsv41-park-N` 并新建
同名占位容器——monitor 永随旧对象（不退出不重建），healthcheck 因 8899 健康（dsv41）而绿。

**注意**：占位容器无重启策略，机器重启后 `vllm-tp4-head` disabled 不拉起、worker 单元 disabled
不拉起，但 `vllm-v4v-head.service` enabled 会自启 Tony 栈——重启前须处理（沿用现有红线）。

**二次穿透**：Boot crash 窗口内 8899 短暂死亡 + 占位容器龄 >15min → healthcheck rm 名字持有容器 →
LuZ monitor 循环重建失败（GPU 被 dsv41 占用，容器 Exited 1）→ 四机重新停靠 + 新增
`dsv41-park-guard.sh` 守护循环（每 10 分钟补名字持有容器，nohup 运行）。**回退注意**：worker
monitor 进程可能处于 unit start-limit 状态，LuZ 自愈链回退路径 = head monitor 重建 + 手动 worker 脚本。

**三次穿透（冷启动窗口）**：dsv41 冷启动数分钟内 8899 死亡，若名字持有容器龄 >15min 则 healthcheck
触发 rm，停靠对象恰好是持有容器时 monitor 醒来重建。**根治协议**：① 守护升级——每 10 分钟 rename
换新持有容器（龄永远 <15min，healthcheck 永不触发），旧持有容器保留为 `dsv41-parkold-` 前缀；
② **任何 dsv41 冷启动/重启前，先 fresh re-park 四机**（kill monitor → rm 持有容器 → 新占位 →
sleep 8 → rename park → 再新占位）；③ 维护旗（`state-tp4/maintenance.flag`）照旧护 dsv41 自愈链。
