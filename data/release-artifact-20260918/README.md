## What the run established

**1. The archive is a self-consistent content-addressed store.**
128 tar members = **123 blobs** + `index.json` + `manifest.json` + `oci-layout` + 2 directory
entries. Every one of the 123 blobs satisfies `sha256(bytes) == its own filename`, so
nothing is truncated or silently substituted. Payload 14,686,175,317 bytes uncompressed.

**2. The reference graph closes.** All 123 blobs are reachable from `index.json`;
**0 unreferenced blobs**. The graph is:

```
index.json
└── OCI index blob            03587ce92d08be1a…   (857 B)
    ├── image manifest        be741c200a22b4cf…   (23,717 B, arm64/linux, 123 layers)
    │   └── image config      9e1036bc6a106e76…   (81,769 B)  ← what workers report as .Id
    └── attestation manifest  4ca1fb49073d417d…   (566 B, docker SBOM/provenance)
        └── attestation config eed6883c9729f7bf…  (167 B) + 1 layer ee720f87489d0576…
```

Blob budget: **5 metadata + 118 layer blobs** (117 distinct image layers + 1 attestation
layer) = 123.

**3. The head/worker image-ID split is two objects, not two opinions.** Node 01 reports
`03587ce9…`, which is the OCI **image-index** digest; nodes 02-04 report `9e1036bc…`, which
is the **image-config** digest. Both live in this archive, both self-consistent. Neither is
a content digest — hence the rule in BUILD-IDENTITY that layer counts and reported image IDs
are not acceptance criteria.

**4. The layer list is highly deduplicated.** 123 diffIDs, **117 distinct**:
`sha256:5f70bf18a086007016e948b04aed3b82103a36bea41755b6cddfaf10ace3c6ef` — an empty tar
(1024 NUL bytes) — appears **7 times**, so 6 of the 123 layers carry no content. The image
config's `history` likewise marks 108 of its 231 steps `empty_layer`.

**5. Every value ever published as this image's "identity" is now accounted for.** All five
are `sha256[:16]` of the *same* 123-entry diffID list under different serializations:

| serialization | value |
|---|---|
| space-joined + trailing newline ← **authoritative** | `4ebef21b6aedbd70` |
| space-joined, no trailing newline | `bb7c2d4b38af0514` |
| newline-joined, no trailing newline | `c8751accc458138c` |
| newline-joined + trailing newline | `38bbe8265458f328` |
| newline-joined + two trailing newlines | `0050285e87c6f408` |

Only the first is asserted by production code (`start.sh`'s `IMGID_TPL`), so only it is
*the* identity; the other four are correct hashes of other real serializations of the same
list. **Publish the byte-exact pipeline together with the value** — see BUILD-IDENTITY.

`e541746d26e31a3f` is the sole exception: it reproduces under **none** of the 32 candidate
serializations tested against this archive (not any serialization of the diffID list, not
the config blob, not either manifest, not `index.json`, not the compressed-layer list), and
no production script asserts it. It is labelled **unverifiable**, not "wrong".

## Why this directory exists

A published hash the reader cannot re-derive is a claim, not a proof. The artifact now ships
with the script that recomputes its identity from the artifact alone, and this directory
records the run so the numbers in `README.md` and `BUILD-IDENTITY.md` can be checked without
downloading 13.5 GiB.
