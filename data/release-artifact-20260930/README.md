## What the run established

**1. The archive is a self-consistent content-addressed store.**
16 tar members = **11 blobs** + `index.json` + `manifest.json` + `oci-layout`
+ 2 directory entries. Every one of the 11 blobs satisfies
`sha256(bytes) == its own filename` — measured `blob hash failures: 0` — so nothing is
truncated or silently substituted. Payload 14,055,764,167 bytes.

**2. The reference graph closes.** All 11 blobs are reachable from `index.json`
(`1` descriptor); **0 unreferenced blobs**. The graph is:

```
index.json                        (395 B)
└── OCI index blob               f51d0f2ac9b47adf…   (856 B)
    ├── image manifest           e15d95c7cd893aa5…   (5 layers, config c575f041fec2ec98…)
    │   └── image config         c575f041fec2ec98…   (6677 B)  ← RepoTags dsv41-sglang-optimized:0.2.9-ep1q2-fin2
    └── attestation manifest     cbe4d600c29de5bb…   (1 layer, docker provenance)
        └── attestation config   …
```

Blob budget: metadata + **5 image layer blobs** + 1 attestation layer = 11.

*compressed* blob's sha256 equals its filename (pass 1), **and** the *decompressed*
stream's sha256 equals the config's `diff_id` (pass 2):

> **Why 0.2.9 has five layers where 0.2.8 had three.** The layer count is a property of
> how the image was built, not of the payload: adjacent versions cannot be told apart by
> counting layers, and a layer that adds no files still occupies a position in the chain
> (0.2.8's third layer decompresses to an empty tar for exactly this reason). The
> authoritative binding is the **layer list**, not its length.

## Why this directory exists

A published hash the reader cannot re-derive is a claim, not a proof. The artifact ships
with the script that recomputes its identity from the artifact alone, and this directory
records the run so the numbers in `README.md` and `BUILD-IDENTITY.md` can be checked
without downloading 13 GiB — including the compressed↔uncompressed layer chain, which is
what actually ties a "docker save" file to a runnable image.

> **This directory was completed on 2026-10-01.** As first published it carried only
> `IMAGE-IDENTITY.txt`, `ADAPTER-MANIFEST.txt` and the `.sha256`, while README §7 pointed
> at it for "recorded offline audit and identity data" — so for 0.2.9 the pointer led to
> the identity constants but not to the audit that proves them. The three evidence files
> above were generated by re-running the verifier against the distributed tar; nothing
> was back-filled from the 0.2.8 record.
